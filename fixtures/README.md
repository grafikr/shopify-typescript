# Fixtures

Real responses captured from a Shopify store. They are the source of truth for
the types: `tests/fixtures.test-d.ts` (generated by `pnpm generate`) asserts that
each file matches its type, with no undeclared keys.

```
fixtures/
  js/       .js URLs and the cart API  (/cart.js, /cart/add.js, /products/x.js, …)
  json/     .json URLs                 (/products/x.json, /collections.json, …)
  liquid/   `{{ x | json }}` output    (product, cart, collection, article, paginate)
  global/   `window.Shopify`
```

File names are `<entity>-<scenario>.json`, for example `cart-with-percent-discount-code.json`.
`scripts/generate-tests.mjs` maps file names to types, so a new fixture with a
new name pattern needs a rule there (the script fails and lists unmatched files).
Run `node scripts/generate-tests.mjs --list` to see which type each fixture is checked against.

## Capturing

The fixtures were captured from a development store. Carts need a cookie jar so
cart state is kept between requests:

```sh
J=$(mktemp -u).jar
curl -s -b $J -c $J -X POST "$STORE/cart/add.js" \
  -H 'Content-Type: application/json' -d '{"items":[{"id":123,"quantity":1}]}'
curl -s -b $J -c $J "$STORE/cart.js"
```

### Liquid

Liquid output is captured with a throwaway alternate template that prints the
object as JSON. For example `templates/product.typegen.liquid`:

```liquid
{% layout none %}
{{ product | json }}
```

and then `GET /products/<handle>?view=typegen`. Remove the template afterwards.
Liquid refuses `| json` on some objects (`page`, `blog`, `search`), so those only
have `.json` endpoint types. For pagination use
`{% paginate collection.products by 2 %}{{ paginate | json }}{% endpaginate %}`.

### Edge cases worth capturing

Products with no description, SKU, barcode, images or media; multiple options; a
variant image; a gift card; carts with automatic discounts, percentage and
fixed-amount codes, an invalid code, and a free-shipping code; every cart endpoint
and its error responses; an empty collection; a page with no body; an article with
and without image, summary and tags.

### Where fixtures came from

Most fixtures were captured from a development store, with test data created for the
purpose. The `browsing-context-*suggestion*` fixtures were captured from a public
third-party storefront, because suggestions need a store with several
markets and a visitor whose detected country differs from the excluded one. They
only contain country and language names. To reproduce them:

```sh
curl -sg -H 'Accept-Language: da-DK,da;q=0.9' \
  "$STORE/browsing_context_suggestions.json?country[enabled]=true&country[exclude]=SE&language[enabled]=true&language[exclude]=sv"
```

### Anonymizing

Captured responses are anonymized before they are committed. Types only depend on the
shape of the data, so none of this changes what a fixture proves:

- The shop domain is `shop.myshopify.com`, the shop name is `Shop`, and the shop and theme
  ids are made up. The shop id is also encoded in CDN paths (`/files/1/1234/5678/9012/`).
- Long content fields (`description`, `body_html`, `content`, `body`, `summary_html`,
  `product_description`) are `"Content"`. The `description` of cart errors and selling
  plans is not content and is kept.
- File URLs keep their folders, host and `?v=` query, but the filename is replaced by
  `image-001.jpg`, `video-001.mp4` or `model-001.glb`. The same original file gets the same
  new name everywhere, so images that were identical stay identical.
